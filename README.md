# APT Stock Portal

Daily finished-goods stock reporting for **Axis Plastics Transition (APT)** — replaces the customer WhatsApp stock-status group.

Factory operators enter the physically available quantity of every finished-goods part once a day; the report is published as the single official stock record for that date; the customer sees published reports only; the manager sees every change with server timestamps.

**Stack:** Next.js 15 (App Router, TypeScript) · React 19 · Tailwind CSS 4 · Supabase (PostgreSQL, Auth, Row Level Security) · Vercel · Zoho Books API.

## 1. What's in the app

| Role | Login lands on | Can do |
|---|---|---|
| **ADMIN** (manager) | `/admin` | Everything below, plus users, catalogue/units, Zoho sync, full audit log, audited amendments of published reports |
| **STOCK_OPERATOR_1 / _2** | `/entry` | Today's draft: enter/save quantities, see completion, submit the report; read report history and published stock |
| **CUSTOMER** | `/stock` | Read-only published reports, search/filter, per-part history, Excel/CSV export |

Screens:

- **Daily stock entry** (`/entry`) — spreadsheet-style grid of all reportable parts. Search by name / part code / SKU / description; filters (pending, saved, unsaved, needs attention); 25/50/100/all rows; Enter/↓/↑ moves between rows; completion bar; save draft; submit with confirmation. Zero is accepted; negatives, non-numbers and >3 decimals are rejected (client-side and again in the database). Unsaved edits survive an accidental tab close (browser-local backup) and the page warns before leaving. Picks up the other operator's saves every 45 s.
- **Concurrency** — each entry has a revision number. A save sends the revision the operator last saw; if the other operator saved in between, that row is **not** written and is shown as a conflict ("Keep saved" / "Use mine"). Submitting with a stale report version is refused.
- **Customer dashboard** (`/stock`) — latest published report date, parts in catalogue, parts reported, last updated time, searchable table, per-part 30-report history, date picker for previous reports, Excel/CSV export. If today has no published report it says so explicitly and labels the figures with their real date — older stock is never presented as today's.
- **Report history** (`/reports`) and **report register** (`/reports/YYYY-MM-DD`) — every entry with first-entered and last-modified server timestamps and the user responsible; admin can record **amendments** (new quantity + mandatory reason), listed in an amendment history.
- **Audit & activity** (`/activity`, admin) — every quantity entry/change/amendment with original and revised quantity, user, exact time (IST), operation and report; filters + Excel/CSV export.
- **Catalogue & units** (`/admin/catalogue`) — configure the 60 parts that have no unit in Zoho, include/exclude parts from the daily report, view services and inactive items.
- **Users & access** (`/admin/users`) — create logins (operators slot 1/2, customer, admin), edit role/name, deactivate, reset password.
- **Zoho Books sync** (`/admin/zoho`) — integration status, OAuth connect, sync now, import the bundled export, sync log.

Timestamps are generated by PostgreSQL (`now()`), stored as `timestamptz` (UTC) and displayed in the factory timezone from `app_settings.factory_timezone` (initially `Asia/Kolkata`). The factory date used for "today's report" is computed in the database, not the browser.

## 2. Security model

Authorization is enforced **in the database**; the UI only mirrors it.

- **RLS is enabled on every table.** Policies grant `select` only, scoped by role (`current_app_role()`, which also requires `profiles.is_active`). Users without an active profile — including anyone who signs up on their own — can read nothing.
- **No client writes to tables.** All writes go through `SECURITY DEFINER` functions that check the caller's role and validate input: `get_or_create_today_report`, `save_draft_entries`, `submit_report`, `amend_entry`, `admin_set_item_unit`, `admin_set_item_inclusion`, `admin_upsert_profile`.
- **Customers never touch raw tables.** They read through `published_reports`, `published_report_stock`, `published_item_history`, which return published data only and no operator identities.
- **Triggers protect history** even against privileged connections (the only exception is the admin's explicit permanent-delete functions, migration 0007): server-stamped timestamps/identities on every entry; published entries can only change through `amend_entry`; entries and published reports cannot be deleted; a report cannot return to draft or change its date; `audit_logs` and `report_amendments` are append-only (update/delete/truncate raise errors).
- **Server-only secrets**: `SUPABASE_SERVICE_ROLE_KEY`, Zoho credentials and `CRON_SECRET` are read only in server code (`import "server-only"`). The service-role client is used only after the caller is verified as admin (or by the cron route with its secret). Zoho tokens live in `zoho_oauth_tokens`, which has RLS on, no policies and privileges revoked from `anon`/`authenticated`.
- Every page and server action also checks the role server-side (`requireProfile` / `assertRole`); middleware refreshes the Supabase session and redirects signed-out users.
- Exports run as the signed-in user, so RLS decides what can be exported. CSV cells are protected against spreadsheet formula injection.

## 3. Database & migration 0003

Existing migrations `0001_initial_schema.sql` and `0002_entry_timestamps_and_manager_audit.sql` are kept unchanged. **`0003_production_hardening.sql` builds on them and is non-destructive**, and **`0004_explicit_table_grants.sql`** adds the explicit read-only table privileges that newer Supabase projects require (without it every page read fails with *permission denied for table …*): no table or column is dropped and no row is deleted. It is idempotent (safe to re-run).

What 0003 changes:

| Area | Change |
|---|---|
| `app_settings` (new) | `factory_timezone = Asia/Kolkata`; `factory_today()` helper |
| `profiles` | adds `email`, `operator_slot` (1/2, max two active operators), `updated_at`; removes the broad "admins manage profiles" write policy (admin writes go through an audited function) |
| `zoho_items` | adds `sku`, `description`, `include_in_stock`, `unit_source`, `unit_configured_by/at`, `zoho_last_modified_time`, `created_at`, `updated_at`; **tightens catalogue read** to users with an active portal role (0001 allowed any authenticated user); replaces the admin write policy with read-only |
| `daily_reports` | adds `version` (optimistic locking), `last_modified_by`, `published_item_count`, `amended_at/by`, `amendment_count`; removes direct insert/update policies and the customer table policy; triggers block deletion of published reports, date changes and un-publishing |
| `daily_stock_entries` | adds `created_at`, `created_by(_name)`, `updated_by_name`, `report_date`, `item_name_snapshot`, `part_code_snapshot` (back-filled for any existing rows); replaces the 0002 trigger with stamp + audit triggers; blocks deletes and direct edits of published entries; removes direct write and customer policies |
| `audit_logs` | adds `actor_name`, `operation`, `report_id`, `report_date`, `zoho_item_id`, `old_quantity`, `new_quantity`; made append-only (existing rows are kept) |
| `report_amendments` (new) | append-only amendment history |
| `zoho_sync_runs`, `zoho_oauth_tokens` (new) | sync log; server-only token store |
| Functions | role-checked RPCs listed in §2; function `EXECUTE` revoked from `public`/`anon` |

All of this is covered by the automated database tests (§7), which apply 0001 → 0002 → 0003 → seed to a fresh database every run, and re-applying 0003 has been verified to be a no-op.

## 4. Local setup (Windows / PowerShell)

Requires **Node.js 20.9+** (22 LTS recommended).

```powershell
cd E:\APT_2026\apt\apt-stock-portal-starter\apt-stock-portal
node -v
npm -v
npm install
```

Your existing `.env.local` already holds `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_ANON_KEY`. Open `.env.example`, copy any further variables you need into `.env.local` (at minimum `SUPABASE_SERVICE_ROLE_KEY` for creating users), then:

```powershell
npm run dev
```

Open http://localhost:3000. Before Supabase is configured the app shows a configuration page.

Other scripts:

```powershell
npm run typecheck   # TypeScript
npm test            # unit tests
npm run test:db     # database/RLS tests (needs a local PostgreSQL, see §7)
npm run test:remote # read-only permission checks against your real Supabase project
npm run build       # production build
npm run seed:build  # regenerate supabase/seed/zoho_items_seed.sql from data/zoho-items.json
```

## 5. Supabase setup

### 5.1 Inspect the remote database first

Open **Supabase Dashboard → SQL Editor** and run `supabase/check_existing_schema.sql`. It is read-only and shows which tables exist, row counts, whether 0002/0003 are applied, the current policies and the CLI migration history. (The last query errors harmlessly if the CLI history schema does not exist — that means migrations were applied by hand, or not at all.)

### 5.2 Protect existing data

If any table above has rows you care about, take a backup first: Dashboard → **Database → Backups** (paid plans), or with the CLI (needs Docker Desktop):

```powershell
npx supabase db dump --linked -f backup_schema.sql
npx supabase db dump --linked --data-only -f backup_data.sql
```

### 5.3 Apply migrations — option A: Supabase CLI (recommended)

```powershell
npx supabase login
npx supabase init                       # only if supabase\config.toml does not exist; keeps existing migrations
npx supabase link --project-ref <your-project-ref>   # asks for the database password
npx supabase migration list             # compare local vs remote
```

- If **0001/0002 were already run by hand** in the SQL editor (the remote column is empty but the tables exist), mark them as applied so the CLI does not re-run them:
  `npx supabase migration repair --status applied 0001 0002`
- Preview, then apply:

```powershell
npx supabase db push --dry-run
npx supabase db push
```

### 5.3 Apply migrations — option B: SQL editor

Paste and run, in order, only the files not yet applied: `0001_initial_schema.sql`, `0002_entry_timestamps_and_manager_audit.sql`, `0003_production_hardening.sql`, `0004_explicit_table_grants.sql`, `0005_allow_partial_reports.sql`, `0006_manual_items.sql`, `0007_admin_permanent_delete.sql`, `0008_admin_delete_users.sql`, `0009_hourly_updates.sql`.

### 5.4 Load the catalogue

Either run `supabase/seed/zoho_items_seed.sql` in the SQL editor, or (after creating the admin) use **Admin → Zoho Books sync → Import bundled catalogue**. Both upsert the 235 goods from the supplied export; re-running is safe.

### 5.5 Authentication settings (Dashboard → Authentication)

- **Disable public sign-ups** (Sign In / Providers → "Allow new users to sign up" off). Accounts are created by the admin only. (Even if left on, users without a profile get no data — but turn it off.)
- Email provider: keep enabled (email + password).
- URL Configuration: Site URL = your production URL; add `http://localhost:3000` to redirect URLs for development.
- Recommended: enable leaked-password protection and set a minimum password length ≥ 10.

### 5.6 First administrator

1. Dashboard → Authentication → Users → **Add user** (email + password, *Auto Confirm User*).
2. Edit and run `supabase/bootstrap_admin.sql` with that email.
3. Sign in to the portal; create the two operators and the customer from **Users & access**.
4. In **Catalogue & units**, set the unit for every part flagged *Missing unit* (or exclude parts that should not be reported). Operators cannot enter quantities for a part until it has a unit — the system deliberately does not guess units.

## 6. Zoho Books integration

Status: **framework implemented and unit-tested; not yet connected** — no Zoho credentials were supplied.

How it works: OAuth 2.0 authorization-code flow (admin clicks *Connect Zoho Books*) → refresh token stored server-side → access tokens refreshed automatically → `GET /books/v3/items?filter_by=Status.All` paged at 200 → upsert by Zoho `item_id`. Mapping: `item_id` → permanent key, `name` → display name, `description` → description + part code (first line), `sku` → SKU (optional), `unit` → unit (blank stays blank and is flagged; never invented), `status` → active/inactive, `product_type` → goods/service (services excluded from stock reporting). An empty unit from Zoho never overwrites a unit the admin configured. Every run is logged in `zoho_sync_runs` with counts and errors. A daily Vercel Cron calls `/api/cron/zoho-sync`.

Incremental sync: Zoho documents no modified-since filter for `GET /items`, so each sync is a full, idempotent upsert — about two API requests for the current ~246 items.

**To connect (what's still needed):**

1. Confirm the Zoho data centre of the APT account (`.in` assumed; change `ZOHO_ACCOUNTS_URL` / `ZOHO_API_BASE_URL` if different).
2. https://api-console.zoho.in → *Add Client* → **Server-based Applications**. Homepage: your portal URL. Authorized redirect URI: `https://<your-domain>/api/zoho/callback` (and `http://localhost:3000/api/zoho/callback` for local testing).
3. Set `ZOHO_CLIENT_ID`, `ZOHO_CLIENT_SECRET`, `ZOHO_REDIRECT_URI`, `ZOHO_ORGANIZATION_ID` (Zoho Books → Settings → Organization Profile), `SUPABASE_SERVICE_ROLE_KEY`, `CRON_SECRET`.
4. In the portal: **Admin → Zoho Books sync → Connect Zoho Books** (a Zoho admin approves scope `ZohoBooks.settings.READ`, read-only), then **Sync items now**.

## 7. Testing

| Suite | Command | What it covers |
|---|---|---|
| Unit (27 tests) | `npm test` | quantity validation (zero ok, negatives/invalid rejected), search, timezone display, CSV/XLSX export incl. formula-injection guard, Zoho mapping, pagination, error handling |
| Database & RLS (28 tests) | `npm run test:db` | applies the real migrations to a fresh database and runs the 13 required scenarios as real `authenticated`/`anon` roles with JWT claims (see below) |
| Remote (read-only) | `npm run test:remote` | signs in to **your** Supabase project with test accounts and checks role permissions; changes nothing |

Required scenarios → database tests (`tests/db/portal.test.ts`): 1 operator signs in and is identified as STOCK_OPERATOR_1 · 2 operator enters/updates quantities (revision increments) · 3 zero accepted · 4 negative/non-numeric/over-precise/blank rejected (+ table constraint) · 5 incomplete report and report with missing units cannot be submitted · 6 complete report publishes once; re-submit refused; published report locked · 7 customer sees published stock · 8 customer sees no drafts, audit log, amendments or other profiles · 9 customer cannot edit anything · 10 manager sees server-generated created/modified timestamps and users; client-supplied timestamps overridden · 11 amendment creates amendment + audit records with original/revised quantity, user, time, reason; audit log append-only · 12 stale concurrent save returns a conflict and does not overwrite; stale submit refused · 13 previous report stays accessible and is never shown as today's. Plus: anonymous and profile-less users get nothing; max two operator slots; Zoho upsert keeps admin units and excludes services.

**Running the DB tests** needs a PostgreSQL 15+ server you can drop/create databases on (the tests create and drop a database called `apt_vitest`; never point this at Supabase). On Windows: install PostgreSQL from postgresql.org, then

```powershell
$env:TEST_DATABASE_ADMIN_URL = "postgres://postgres:<password>@localhost:5432/postgres"
npm run test:db
```

The Supabase pieces the migrations rely on (`auth.uid()`, `auth.users`, roles `anon`/`authenticated`/`service_role`, default grants) are emulated by `tests/db/supabase_stub.sql` — test-only, never run it on Supabase.

What these tests do **not** prove: real Supabase Auth sign-in and PostgREST behaviour against your project — run `npm run test:remote` after setup, and do a manual run-through (§9).

## 8. Deploying to Vercel

1. Create a **private** GitHub repository and push (`.env.local` is git-ignored):
   ```powershell
   git init
   git add .
   git commit -m "APT Stock Portal v1"
   git branch -M main
   git remote add origin https://github.com/<org>/apt-stock-portal.git
   git push -u origin main
   ```
2. Vercel → *Add New Project* → import the repository (framework auto-detected). `vercel.json` sets region `bom1` (Mumbai), security headers, `noindex`, and the daily Zoho cron (00:30 UTC = 06:00 IST).
3. Environment variables (Production and Preview):

   | Variable | Required | Exposed to browser |
   |---|---|---|
   | `NEXT_PUBLIC_SUPABASE_URL` | yes | yes (public by design) |
   | `NEXT_PUBLIC_SUPABASE_ANON_KEY` | yes | yes (public by design; RLS protects data) |
   | `SUPABASE_SERVICE_ROLE_KEY` | yes (user admin, Zoho) | **no** |
   | `CRON_SECRET` | yes if Zoho sync scheduled | **no** |
   | `ZOHO_CLIENT_ID`, `ZOHO_CLIENT_SECRET`, `ZOHO_ORGANIZATION_ID`, `ZOHO_REDIRECT_URI` | for Zoho | **no** |
   | `ZOHO_ACCOUNTS_URL`, `ZOHO_API_BASE_URL` | if not India DC | **no** |
   | `ZOHO_REFRESH_TOKEN` | optional | **no** |

4. Deploy to a preview URL first. Add the production URL to Supabase Auth URL configuration and the Zoho redirect URI.
5. Keep the deployment private (Vercel *Deployment Protection*) and do not give the customer a login until §9 is complete.

## 10. Engineering decisions

- **Roles**: database roles stay `admin` / `operator` / `customer` (compatible with 0001); STOCK_OPERATOR_1/2 are `operator` + `operator_slot` 1/2, unique among active operators.
- **One report per factory date** (`daily_reports.report_date` unique). Operators can edit/submit only today's draft (factory timezone); the admin can amend any published report.
- **Hourly stock updates** (owner decision, 21 Nov 2026, migration 0009): instead of one report per day, operators publish an update per interval (admin sets opening hour, closing hour and interval). Operators can edit only the update whose window is open now. A new update starts with the quantities of the latest published update of the same day carried forward, keeping each part's original "last changed" time; the first update of a day starts empty so yesterday's stock is never shown as today's. Customers see the latest update and can browse earlier ones.
- **Partial reports are allowed** (owner decision, 21 Nov 2026, migration 0005). Operators may leave quantities empty; a report needs at least one saved quantity to publish. Empty parts are not part of that day's published report and are not shown to the customer.
- **Operators can add a part that is not in the catalogue** (migration 0006): name, part code, unit and quantity. It gets a `MANUAL-…` ID, is saved into today's draft and kept in the catalogue, and is listed under *Catalogue & units → Added manually* for the admin to review (e.g. exclude it once the real item arrives from Zoho). Exact duplicates of existing names/part codes are refused.
- **Admin permanent delete** (owner decision, migration 0007): the admin can permanently delete a whole report (type the date to confirm), a single line, or a manually added part, each with a mandatory reason. The data is erased; one audit line (who, when, what, reason) is kept. The audit log itself can never be deleted, and outside these three functions all delete protections remain.
- **Admin can delete users** (migration 0008) — only users without stock history (lines, reports, amendments); others must be deactivated so official records stay attributable. Audit lines keep the deleted user's name.
- **Units are never guessed.** Parts without a unit cannot receive quantities until the admin sets the unit (or excludes the part).
- **A saved quantity cannot be cleared**, only changed (0 is valid). This keeps every entry row permanent and avoids revision-reuse edge cases.
- **Snapshots**: entries store the item name, part code and unit at entry time so published history stays accurate if Zoho renames an item.
- **Conflicts are per row**: non-conflicting rows in a save are written; conflicting rows are returned untouched for the operator to resolve.
- **Fonts are self-hosted** (`@fontsource`), so builds and pages do not depend on Google Fonts. The heading face (Barlow Condensed, bold italic) approximates the letterhead lettering; the original typeface was not identifiable.

## 11. Project structure

```
app/
  login/  auth/signout/  setup/            sign-in, sign-out, missing-config page
  (portal)/                                authenticated shell (sidebar, factory date)
    entry/       daily stock entry grid + server actions

  api/export/              CSV/XLSX exports (RLS-scoped)
  api/zoho/authorize|callback   Zoho OAuth
  api/cron/zoho-sync       scheduled sync (CRON_SECRET)
lib/          auth, Supabase clients, Zoho client, formatting, validation, exports
components/   sidebar, brand mark, page header, stat cards
supabase/
  migrations/0001..0003    schema, RLS, functions, triggers
  seed/zoho_items_seed.sql catalogue seed (generated from data/zoho-items.json)
  bootstrap_admin.sql      first admin
  check_existing_schema.sql read-only inspection
data/zoho-items.json       supplied Zoho export (235 goods)
tests/unit, tests/db       automated tests
scripts/                   seed generator, remote verification
```
